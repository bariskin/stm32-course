# Лекция 4. Таймеры и PWM на STM32F407

**Курс:** «STM32: от основ к реальным проектам»  
**Продолжительность:** 90 минут  
**Платформа:** STM32F407, STM32CubeIDE, HAL на C  
**Уровень:** начальный

> Важно: частоты в примерах рассчитаны для тактирования SYSCLK = 168 МГц, APB1 = 42 МГц, APB2 = 84 МГц. Если в вашем проекте другие настройки Clock Configuration, пересчитайте `PSC` и `ARR`. Вывод светодиода и канал таймера на нём зависят от платы — сверьтесь со схемой.

После занятия студент сможет:

- рассчитать `PSC` и `ARR` для нужной частоты событий;
- определить тактовую частоту конкретного таймера STM32F407;
- настроить прерывание таймера по переполнению (update event);
- заменить блокирующую `HAL_Delay()` неблокирующей проверкой времени;
- сформировать PWM-сигнал и менять скважность из программы;
- применить таймер для программного подавления дребезга кнопки из лекции 3.

## 3. Почему `HAL_Delay()` — проблема

```c
while (1)
{
    HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
    HAL_Delay(500);
}
```

Пока выполняется `HAL_Delay(500)`, основной цикл больше ничего не делает: не опрашивает кнопку, не обрабатывает флаги из прерываний, не отвечает по UART. Для одного светодиода это допустимо, для реального устройства — нет.

Решения на этом занятии:
- **аппаратный таймер** сам отсчитывает время и сообщает о событии прерыванием;
- **неблокирующая проверка времени** через счётчик миллисекунд `HAL_GetTick()`;
- **PWM** — таймер формирует сигнал на выводе вообще без участия процессора.

## 4. Устройство таймера

### Основные регистры

| Регистр | Назначение |
|---|---|
| `PSC` (Prescaler) | Делит входную частоту таймера на `PSC + 1` |
| `CNT` (Counter) | Текущее значение счётчика |
| `ARR` (Auto-Reload Register) | Значение, после которого счётчик переходит в 0 и генерирует update event |
| `CCRx` (Capture/Compare) | Порог сравнения для канала x — используется в PWM |

В режиме счёта вверх счётчик идёт 0, 1, 2 … `ARR`, затем снова 0. Каждый переход через `ARR` — **update event** (событие обновления), по нему можно получить прерывание.

### Формула

```
f_cnt    = f_TIM / (PSC + 1)                 — частота счёта
f_update = f_TIM / ((PSC + 1) · (ARR + 1))   — частота событий обновления
T_update = (PSC + 1) · (ARR + 1) / f_TIM     — период
```

`+1` есть в обеих скобках: `PSC = 0` означает деление на 1, `ARR = 999` — 1000 отсчётов.

### Тактовая частота таймера

На STM32F407 таймеры подключены к двум шинам:

| Шина | Таймеры | Частота шины в примере | Частота таймера |
|---|---|---|---|
| APB1 | TIM2–TIM7, TIM12–TIM14 | 42 МГц | **84 МГц** |
| APB2 | TIM1, TIM8–TIM11 | 84 МГц | **168 МГц** |

Правило: если делитель шины APB не равен 1, частота таймеров этой шины вдвое выше частоты самой шины. Поэтому таймеры APB1 тактируются 84 МГц, а не 42 МГц. Это частая причина ошибки «таймер работает в два раза быстрее, чем рассчитано». Точную частоту смотрите на вкладке Clock Configuration (строки `APB1 Timer clocks` и `APB2 Timer clocks`).

### Пример расчёта: событие 1 раз в секунду на TIM6 (84 МГц)

Удобно выбрать `PSC` так, чтобы частота счёта была круглой:

- `PSC = 8399` → f_cnt = 84 000 000 / 8400 = 10 000 Гц (один отсчёт = 0,1 мс);
- `ARR = 9999` → 10 000 отсчётов = 1 с.

Проверка: 84 000 000 / (8400 · 10 000) = 1 Гц.

Ограничение: на TIM6 `PSC` и `ARR` 16-битные (до 65 535). TIM2 и TIM5 имеют 32-битный счётчик и позволяют задавать длинные периоды без большого `PSC`.

## 5. Прерывание таймера

### Настройка в STM32CubeIDE

1. В Pinout & Configuration откройте **Timers → TIM6** и включите **Activated**.
2. В Parameter Settings задайте `Prescaler = 8399`, `Counter Period = 9999`.
3. На вкладке NVIC Settings включите **TIM6 global interrupt, DAC1 and DAC2 underrun error interrupts**.
4. Сохраните `.ioc` и сгенерируйте код.

TIM6 — базовый таймер: у него нет выводов и каналов, только счёт и update event. Для отсчёта интервалов это самый простой выбор.

> Не выбирайте для своих задач тот таймер, который указан в **SYS → Timebase Source**. Если там стоит не SysTick, а, например, TIM7, этот таймер уже занят под `HAL_GetTick()`.

### Запуск

Генерация кода только настраивает таймер. Запустить его нужно самому, после инициализации:

```c
/* USER CODE BEGIN 2 */
HAL_TIM_Base_Start_IT(&htim6);
/* USER CODE END 2 */
```

`HAL_TIM_Base_Start()` без `_IT` запустит счёт, но прерывания не будет.

### Callback

HAL вызывает один callback для update event всех таймеров:

```c
/* USER CODE BEGIN 4 */
volatile uint8_t tick1s = 0;

void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
    if (htim->Instance == TIM6)
    {
        tick1s = 1;
    }
}
/* USER CODE END 4 */
```

Проверка `htim->Instance` обязательна: если в проекте Timebase Source — таймер (например, при FreeRTOS), CubeMX уже создал `HAL_TIM_PeriodElapsedCallback()` в `main.c`. В этом случае **не создавайте вторую функцию**, а добавьте свою ветку в существующую — иначе будет ошибка компоновки (multiple definition).

Как и в лекции 3, в callback только флаг, работа — в основном цикле:

```c
while (1)
{
    /* USER CODE BEGIN 3 */
    if (tick1s != 0)
    {
        tick1s = 0;
        HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
    }
    /* USER CODE END 3 */
}
```

## 6. Неблокирующие задержки на `HAL_GetTick()`

Отдельный аппаратный таймер на каждую задачу не нужен. HAL уже ведёт счётчик миллисекунд, который возвращает `HAL_GetTick()`. Шаблон «запомнить время и проверять разницу»:

```c
uint32_t ledTick = HAL_GetTick();

while (1)
{
    if (HAL_GetTick() - ledTick >= 500U)
    {
        ledTick += 500U;
        HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
    }

    /* здесь выполняются другие задачи — цикл не блокируется */
}
```

Почему именно `HAL_GetTick() - ledTick >= 500`, а не `HAL_GetTick() >= ledTick + 500`:
- счётчик 32-битный и примерно через 49,7 суток переполняется;
- вычитание беззнаковых чисел корректно работает и через переполнение, а сравнение с суммой — нет.

`ledTick += 500` вместо `ledTick = HAL_GetTick()` сохраняет точный ритм: опоздание одной проверки не накапливается.

Каждой задаче — своя переменная времени: так в одном цикле уживаются светодиод на 500 мс, опрос датчика на 100 мс и отправка по UART раз в секунду.

## 7. PWM

### Принцип

В режиме PWM таймер сам управляет выводом канала:
- пока `CNT < CCRx` — на выходе активный уровень;
- когда `CNT ≥ CCRx` — неактивный.

```
частота PWM  = f_TIM / ((PSC + 1) · (ARR + 1))
скважность   = CCRx / (ARR + 1)
```

Процессор лишь записывает новое значение `CCRx`, сигнал формируется аппаратно.

### Расчёт: 1 кГц на TIM4 (84 МГц)

- `PSC = 83` → f_cnt = 1 МГц;
- `ARR = 999` → 1000 шагов, частота PWM 1 кГц;
- `CCR = 0 … 1000` → скважность 0 … 100 % с шагом 0,1 %.

Частота 1 кГц достаточна, чтобы глаз не видел мерцания светодиода.

### Настройка в STM32CubeIDE

1. Найдите на схеме платы светодиод, подключённый к выводу с функцией канала таймера (в Pinout кликните по выводу: в списке будут варианты вида `TIMx_CHy`).
   *Пример:* на плате STM32F4DISCOVERY светодиоды подключены к PD12–PD15, это каналы 1–4 таймера TIM4. На другой плате будет иначе.
2. Назначьте вывод функции `TIM4_CH1` (или своей).
3. В **Timers → TIM4**: Channel1 = **PWM Generation CH1**.
4. Parameter Settings: `Prescaler = 83`, `Counter Period = 999`, `Pulse = 0`, `Mode = PWM mode 1`, `CH Polarity = High`.
5. Сгенерируйте код.

### Код: плавное изменение яркости

```c
/* USER CODE BEGIN 2 */
HAL_TIM_PWM_Start(&htim4, TIM_CHANNEL_1);
/* USER CODE END 2 */

uint32_t fadeTick = HAL_GetTick();
uint16_t duty = 0;
int8_t step = 10;

while (1)
{
    /* USER CODE BEGIN 3 */
    if (HAL_GetTick() - fadeTick >= 10U)
    {
        fadeTick += 10U;

        duty += step;
        if (duty >= 1000U || duty == 0U)
        {
            step = -step;
        }
        __HAL_TIM_SET_COMPARE(&htim4, TIM_CHANNEL_1, duty);
    }
    /* USER CODE END 3 */
}
```

Каждые 10 мс скважность меняется на 1 %. Полный цикл «погас → ярко → погас» занимает около 2 секунд, а основной цикл остаётся свободным.

Объявления `fadeTick`, `duty`, `step` разместите в секции `USER CODE BEGIN 2` или сделайте глобальными — главное, внутри `USER CODE`, чтобы CubeMX не удалил их при регенерации.

> Если светодиод включается низким уровнем (анод на питании), яркость будет инвертирована. Выберите `CH Polarity = Low` или используйте `ARR + 1 - duty`.

## 8. Дребезг кнопки: решение через время

В лекции 3 одно нажатие могло вызывать несколько прерываний. Простое и надёжное решение — игнорировать события, пришедшие слишком быстро после предыдущего:

```c
/* USER CODE BEGIN 4 */
volatile uint8_t buttonEvent = 0;
static uint32_t lastButtonTick = 0;

void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    if (GPIO_Pin == BTN_Pin)
    {
        uint32_t now = HAL_GetTick();
        if (now - lastButtonTick >= 50U)
        {
            lastButtonTick = now;
            buttonEvent = 1;
        }
    }
}
/* USER CODE END 4 */
```

Окно 50 мс перекрывает типичный дребезг механической кнопки и не мешает нажимать быстро. `HAL_GetTick()` в callback допустим: это чтение переменной, а не ожидание. Условие — приоритет прерывания SysTick (Timebase) должен быть выше приоритета EXTI, иначе счётчик не будет обновляться во время длительной обработки. В проекте по умолчанию это выполняется.

Более строгий вариант — запускать из EXTI однократный таймер и проверять уровень входа после его истечения. Его мы разберём позже вместе с FreeRTOS.

## 10. Типичные ошибки

| Симптом | Что проверить |
|---|---|
| Прерывание таймера не приходит | Вызван ли `HAL_TIM_Base_Start_IT()`, включён ли IRQ в NVIC |
| Частота в 2 раза выше расчётной | Взята частота шины APB вместо `APB Timer clocks` |
| Частота немного не совпадает | Забыт `+1` в `PSC + 1` или `ARR + 1` |
| Ошибка multiple definition | Второй `HAL_TIM_PeriodElapsedCallback()` — объедините в одну функцию |
| Сломался `HAL_Delay()` / `HAL_GetTick()` | Использован таймер, выбранный в SYS → Timebase Source |
| Нет сигнала PWM | Вызван ли `HAL_TIM_PWM_Start()`, назначен ли вывод функции `TIMx_CHy` |
| Яркость инвертирована | Полярность канала или схема включения светодиода |
| Светодиод мерцает | Слишком низкая частота PWM |
| Сбой через ~50 суток работы | Сравнение `GetTick() >= t + N` вместо разности |

## 11. Контрольные вопросы

1. Какой будет частота событий обновления при f_TIM = 84 МГц, `PSC = 839`, `ARR = 99`?
2. Почему таймеры APB1 на STM32F407 в типичной конфигурации работают на 84 МГц, а не на 42 МГц?
3. Чем отличаются `HAL_TIM_Base_Start()` и `HAL_TIM_Base_Start_IT()`?
4. Почему в `HAL_TIM_PeriodElapsedCallback()` нужно проверять `htim->Instance`?
5. Почему `HAL_GetTick() - t >= N` корректно работает при переполнении счётчика?
6. Как при `ARR = 999` получить скважность 25 %?
7. Почему для фильтра дребезга не используют `HAL_Delay()` в callback?

### Ответы для преподавателя

1. 84 000 000 / (840 · 100) = 1000 Гц.
2. При делителе APB1, не равном 1, тактирование таймеров этой шины удваивается.
3. Первая только запускает счёт, вторая дополнительно разрешает прерывание по update event.
4. Callback общий для всех таймеров, включая таймер Timebase HAL.
5. Беззнаковое вычитание выполняется по модулю 2³², поэтому разность остаётся верной.
6. `CCR = 250`.
7. Задержка в ISR блокирует программу и другие прерывания с меньшим приоритетом; а если SysTick имеет более низкий приоритет, `HAL_Delay()` может зависнуть навсегда.

## 12. Выводы

- Таймер — независимый от процессора счётчик: `f_update = f_TIM / ((PSC+1)(ARR+1))`.
- Частоту таймера берите из `APB Timer clocks`, а не из частоты шины.
- Генерация CubeMX не запускает таймер — нужны `HAL_TIM_Base_Start_IT()` или `HAL_TIM_PWM_Start()`.
- В callback — только флаг и проверка источника.
- `HAL_GetTick()` с разностью времени заменяет `HAL_Delay()` и позволяет выполнять несколько задач в одном цикле.
- PWM формируется аппаратно; программа меняет только `CCR`.
